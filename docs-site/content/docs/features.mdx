## Dashboard

<AppLink path="/runs">**Runs**</AppLink> lists every reviewed pull request with its [status](/how-it-works#details). Click a
run to see its steps, the diff with findings, and **Cancel** or **Restart**.

The dashboard is in English by default. To switch to Russian, open the profile menu at the bottom
of the sidebar and pick **Русский** under **Language**, next to the theme. The choice is saved in your
browser.

## Workspace settings

<StatusBadge /> Workspace settings will appear in the sidebar. The page will show workspace
configuration, identity details, and upcoming team and billing management for the active workspace.

### General

<StatusBadge /> The **General** section will display the essential identity and access details
of the current workspace. Every role sees this section, also in the read-only mode:

- **Workspace name**: The display name of the workspace.
- **Workspace ID**: The unique identifier of the workspace, with a one-click copy button.
- **GitHub App Installation ID**: The numeric installation identifier of the GitHub App for this
  workspace.
- **Your role**: Your active role badge: **Owner**, **Admin**, **Billing**, **Member**, or
  **Read only**.

### Team and access

<StatusBadge /> The **Team and access** section will manage teammates, invitations, and role
assignments. Full member management is planned under upcoming updates.

Access will be restricted by workspace role:
- **Owner** and **Admin** can view and manage workspace members.
- Teammates with **Billing** or **Member** roles see an access notice explaining that team
  management is available only to the Owner and Admins of the workspace.

### Billing and plan

<StatusBadge /> The **Billing and plan** section will cover subscription tiers, usage, and payment
methods. Full billing self-service is planned under upcoming updates.

Access will be structured by workspace role:
- All roles (**Owner**, **Admin**, **Billing**, and **Member**) will be able to view workspace
  usage, balance, and active plan.
- Managing subscriptions, payment cards, auto-recharge, and balance top-ups will be restricted to
  **Owner**, **Admin**, and **Billing** roles.

### Role permissions matrix

<StatusBadge /> The role permissions model defines capabilities for key actions across workspace
roles:

| Action | Owner | Admin | Billing | Member |
| --- | --- | --- | --- | --- |
| View usage, balance, and plan | Yes | Yes | Yes | Yes |
| View runs, diffs, and findings | With GitHub repo access | With GitHub repo access | With GitHub repo access | With GitHub repo access |
| Trigger and restart reviews | Yes | Yes | No | Yes |
| Top up balance, manage payment cards | Yes | Yes | Yes | No |
| Manage subscription plan, auto-recharge, VAT ID | Yes | Yes | Yes\* | No |
| Request 14-day refund (EU and EEA consumers) | Yes | Yes | Yes | No |
| Manage repository settings, rules, and RAG | Yes | Yes | No | No\*\* |
| Manage integrations (GitLab, Bitbucket) | Yes | Yes | No | No\*\* |
| Invite, edit, and remove team members | Yes | Yes (except Owner) | No | No |
| Assign and revoke Owner role | Yes (min 1 Owner) | No | No | No |

\* Switching to Starter with more than 5 repositories (from Pro, from pay as you go or as a new
Starter plan) is confirmed only by an Owner or Admin, who picks the 5 repositories.

\*\* Until the workspace has its first Owner, repository and integration settings stay open to
every member with GitHub access to the repository.

### Read-only fail-safe mode

<StatusBadge /> If the server does not send your role, or sends one the dashboard does not know,
workspace settings will fall back to a read-only fail-safe mode with **Member** permissions:

- A read-only notice informs the user that their workspace role is unavailable.
- The role badge shows **Read only**.
- Allows safely reviewing workspace identity details without errors or broken navigation.

## Repository settings

In the dashboard, open <AppLink path="/repositories">**Repositories**</AppLink> and click the gear next to a repository. Review rules
live in `.review/rules.md` in the repository itself, see [Rules file](/rules-file).

**Automatic review** turns reviews on or off for the repository. Today a pull request still needs
the `ai-review` label. <StatusBadge /> Soon: on reviews every pull request automatically, off
reviews only pull requests with the label.

<AutoReviewSnippet />

| Setting | What it does |
| --- | --- |
| **CI waiting** | When to start: Auto, Always or Never, see [CI waiting](/how-it-works#details). |
| **Comment limit** | How many findings are posted inline, from 1 to 10. |
| **Verdict** | Post blocking reviews as a comment or as Request changes. |

<ReviewOptionsSnippet />

| Setting | What it does |
| --- | --- |
| **Branch filter** | Review only pull requests into matching branches, for example `main` or `release/*`. Empty means all. |
| **Severity threshold** | `All`, `Warn & Crit` (drops `info`) or `Only Critical` (keeps `critical` and `high`). |

<BranchesSeveritySnippet />

<Accordions>
<Accordion title="Branch filter masks">

One mask per line, up to 20. `*` matches within one part of the name, `**` also crosses `/`.
The characters `? [ ] { } ! \ ~ ^ :` are not allowed. A pull request into a branch outside the
filter is skipped. Findings below the severity threshold are not posted; the `AI Review` check
says how many were hidden.

</Accordion>

## Code index (RAG)

The **RAG** switch builds an index of the default branch: which symbols each file defines and
which files import each other, without the code text. A review uses it to find unchanged code
that depends on the pull request: files that import or use what it changed, and code that still
imports something it removed. Reviewer reads them at the pull request's commit and sends them to
the model with the diff, so the model can see code the change may break. Findings still go on
changed lines.

The excerpts take at most 4,000 tokens of the review input, so a review may cost more. Building
the index calls no model.

The switch is off by default and works only for GitHub repositories. If the index is not built
yet, is being built or failed, the review runs without it and does not wait. An index that is
behind the default branch is still used. A review of only the file list, over 3,000 changed
lines, gets no excerpts.

<RagSnippet />

<Accordions>
<Accordion title="What is indexed and when it is deleted">

Python, TypeScript, JavaScript and Go files. Secrets, vendored folders, generated files and
`review-ignore` matches are skipped. The index updates after pushes to the default branch. A
build stops at fixed limits, for example a 100 MiB archive or 15 minutes, and then shows
**Error**; switch RAG off and on to try again. The index is deleted when you switch RAG off, when
the repository leaves the installation, and after 30 days without reviews. After the 30 days,
the next review rebuilds it. After you switch RAG off, switch it on again to rebuild it. A
repository that comes back to the installation with RAG on rebuilds it by itself.

</Accordion>
</Accordions>
