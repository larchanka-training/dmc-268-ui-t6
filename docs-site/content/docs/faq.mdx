## Access and data

### Which access does Reviewer need?

The GitHub App reads code and pull requests, posts reviews and checks, and creates the
`ai-review` label. GitHub shows these repository permissions when you install it: pull requests
(write), checks (write), issues (write, needed to create the label), contents (read), metadata
(read), actions (read) and commit statuses (read). It has no organization or account permissions
and cannot push code.

It works only in the repositories you pick when you install it. If you pick **All
repositories**, that means every current and future repository of the account. To add or remove
repositories, change the installation on GitHub, then click **Refresh access** in the dashboard.

You sign in to the dashboard with GitHub too, and see the repositories of the installations your
GitHub account can access.

### Who can see my reviews in the dashboard?

People who sign in with a GitHub account that has access to the same installation and
repository. Access ends when the repository leaves the installation.

### What is sent to the AI model?

- The diff of the pull request.
- Its title, description, author, source and target branch, labels and commit messages.
- The root `AGENTS.md`, if there is one.
- A summary of your project's conventions. To write it, Reviewer also sends the file tree and up
  to 10 files of the branch your pull request targets.
- Built-in review guidelines.

Lock files, build output, binaries and files that match `review-ignore` are not sent. The text
of `.review/rules.md` is not sent yet, see [Rules file](/rules-file).

### What does Reviewer store?

- Runs, kept with no time limit; removing the app does not delete them. A run holds the diff, the
  findings and the step log you see in the dashboard, including the model's answer. The prompt
  sent to the model is not stored.
- A snapshot of `.review/rules.md` and the root `AGENTS.md` as read for each run, kept with the
  run.
- A copy of `.review/rules.md` from the default branch, shown in **Review rules**.
- The generated summary of your project's conventions, reused across reviews.
- A cache of file contents, used for up to 7 days.
- The GitHub webhook payloads Reviewer receives, deleted 30 days after they are processed.
- If RAG is on, the code index: structure only (symbols, imports, paths, line numbers), no code
  text.

### Does Reviewer run my code?

No. It does not check out, build or run anything from your repository. It reads text through
the GitHub API.

### Can a pull request trick the reviewer?

Reviewer tells the model to treat code, the description and commit messages as data, never as
instructions. Rules and `AGENTS.md` come only from the base commit, so a pull request cannot
change the rules it is reviewed with. This lowers the risk of prompt injection but cannot rule it
out, so treat the review as advice from a teammate.

## Cost

### How much does it cost?

There is no pricing or billing in the product yet. Each run has a fixed spending limit for the
model; a run that would go over it stops with `budget_exceeded`. RAG adds no cost today.

## Support

### Does it work with GitLab?

GitHub today; GitLab support is coming.

## Troubleshooting

### No review appeared

Check these in order:

1. **The label.** It must be exactly `ai-review`. If it was deleted from the repository, create
   it again with that name. On GitHub, only people with triage access or higher can add labels.
2. **The repository.** It must be connected, with **Automatic review** on. If it is missing from
   **Repositories**, click **Refresh access**.
3. **The pull request** is open and targets a branch that matches the branch filter.
4. **CI.** By default the review waits until the other checks pass. A failed or stuck check keeps
   it waiting. Fix CI, or set **CI waiting** to Never.
5. **Already reviewed.** Each commit is reviewed once. Push a new commit or click **Restart** on
   the run.
6. **The run.** Open **Runs**. A skipped or failed run shows the reason.

### A run was skipped

| Reason | What it means |
| --- | --- |
| `rule_not_matched` | The target branch does not match the branch filter. |
| `all_changes_ignored` | Every changed file is ignored, build output or binary. |
| `no_changes` | The pull request has no changed files. |
| `repo_disabled` | **Automatic review** was switched off before the run started. No check is posted. |
| `budget_paused` | The daily budget is used up, reviews are paused. |

### A run failed

| Code | What to do |
| --- | --- |
| `policy_access_denied`, `policy_revision_unavailable`, `policy_fetch_transient`, `policy_rate_limited` | Reviewer could not read the rules from GitHub; the file itself may be fine. `policy_fetch_transient` and `policy_rate_limited` are retried automatically. Otherwise check the installation, then restart the run. |
| `policy_...` | The rules file or `AGENTS.md` has a problem. The check shows the file, line and fix, see [Rules file](/rules-file#errors-fail-the-run). |
| `llm_context_overflow` | The change does not fit in the model context. Split the pull request. |
| `budget_exceeded` | The run hit its spending limit. Split the pull request. |
| `deadline_exceeded` | The run took too long. Restart it. |
| `github_forbidden` | The GitHub App lost access to the repository. Check the installation. |

Temporary model and GitHub errors are retried automatically. If every attempt fails, restart the
run later.

### The review has no line comments

The pull request may have more than 3,000 changed lines, so only the file list was reviewed. Or
the findings could not be tied to changed lines; then they are in the review body.

### My rules change did nothing

Rules are read from the base commit, so merge the change first. Also note that today only the
`review-ignore` block affects reviews; the rest of the file is checked but not yet sent to the
model.
