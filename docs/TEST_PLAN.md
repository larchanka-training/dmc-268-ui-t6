## 2. Тестирование микросервисов и архитектурных инвариантов

### 2.1. Схлопывание задач (Coalescing Engine, Р-2)
* **Бизнес-цель:** Защита бюджета токенов LLM при частых пушах разработчика в один и тот же PR.
* **Ключ схлопывания:** Кортеж `(installation_id, repo_id, pr_number)`.
* **Тест-кейсы QA:**
  1. **Серия быстрых пушей:**
     - **Действие:** Эмулируем 3 события `push` в один PR с интервалом в 2 секунды (хэши: `sha_1`, `sha_2`, `sha_3`).
     - **Ожидание:** Первые две задачи для `sha_1` и `sha_2` переводятся в статус `state = 'cancelled'`. В работу берется **только последняя задача** с актуальным `head_sha = sha_3`.
  2. **Поздняя отмена (Worker in-flight cancel):**
     - **Действие:** Новый push приходит в момент, когда воркер уже выполняет анализ старого `sha_1`.
     - **Ожидание:** Воркер получает сигнал прерывания (или Publisher проверяет актуальность перед отправкой) и отменяет публикацию устаревших замечаний.

### 2.2. WebHook Processor («Дежурный по GitHub»)
* **Что тестирует QA:**
  1. **Проверка HMAC-подписи:** Вебхуки с некорректным или отсутствующим `X-Hub-Signature-256` отклоняются со статусом `401/403`.
  2. **Идемпотентность (Idempotency Key):** Повторная отправка идентичного вебхука с тем же `X-GitHub-Delivery` не создает дублирующую задачу в RabbitMQ.
  3. **Быстрый ACK:** Обработка и подтверждение приема вебхука выполняется за $< 500$ мс.

### 2.3. Маршрутизация и движки анализа (DiffEngine vs SandboxEngine, Р-3)
* **Что тестирует QA:**
  1. **Тестирование роутера (Router Policy):**
     - Если в конфигурации проекта указан базовый аудит $\to$ задача идет в быстрый **DiffEngine** (SLA 10–40 с).
     - Если активированы правила глубокого анализа/выполнения $\to$ задача идет в **SandboxEngine**.
  2. **Безопасность песочницы SandboxEngine (Network & Secret Isolation):**
     - **Network Isolation:** Контейнер песочницы запускается с флагом `--network=none`. Попытка выполнить исходящий сетевой запрос из песочницы блокируется.
     - **Secret Sanitization:** Проверка окружения контейнера — переменные среды с токенами GitHub, базы данных и ключами LLM API **не пробрасываются** внутрь песочницы.

### 2.4. Публикация результатов: Batch Review (Р-5)
* **Архитектурный стандарт:** Запрещена отправка множества одиночных комментариев. Публикация выполняется **единым батч-запросом**.
* **Эндпоинт:** `POST /repos/{owner}/{repo}/pulls/{pull_number}/reviews`
* **Что тестирует QA:**
  1. **Формирование Batch Payload:** Все найденные замечания упаковываются в массив `comments: [{path, line, body}]`, а общее заключение — в поле `body` ревью с вердиктом `COMMENT` / `REQUEST_CHANGES`.
  2. **Hunk Matching (Защита от сбоя координат):**
     - **Тест:** Модель вернула замечание на строку вне зоны измененного дифа.
     - **Ожидание:** Валидатор отсекает строку из массива `comments` и переносит замечание в текст общего резюме, предотвращая ошибку `422 Unprocessable Entity` от GitHub API.
  3. **Поддержка 1-Click Suggestions:** В поле комментария формируется синтаксис ```suggestion ... ```, отображающий рабочую кнопку применения фикса в UI GitHub.

### 2.5. Инфраструктура и безопасность (RabbitMQ, Sub-network, JWT)
* **Durable Queues & Dead-Letter Queue (DLQ):** При аварийном падении воркера сообщение не теряется, а возвращается в очередь. Невалидные сообщения после 3 попыток отправляются в DLQ.
* **Sub-network Isolation:** Порты RabbitMQ, базы данных PostgreSQL и воркеров закрыты для внешнего трафика и доступны только внутри внутренней сети.
* **JWT Auth:** Все запросы к API Server требуют валидный Bearer-токен. Без токена или с просроченным токеном $\to$ `401 Unauthorized`.

## 3. Методология оценки качества LLM (LLM Evaluation & DoD)

### 3.1. Матрица ошибок (Ground Truth Mapping)
Каждое замечание модели в тестовом прогоне сопоставляется с эталонной спецификацией:

| Обозначение | Определение в контексте AI-ревью | Пример |
| :--- | :--- | :--- |
| **True Positive (TP)** | Реальный баг найден, указана верная строка и корректное объяснение. | Бот нашел SQL-инъекцию на строке 42. |
| **False Positive (FP)** | Ложное срабатывание, придирка к чистому коду или галлюцинация. | Бот утверждает, что функция `x` не объявлена, хотя она есть в проекте. |
| **False Negative (FN)**| Модель пропустила реальный баг, заложенный в эталонном тесте. | Модель не заметила хардкод токена AWS. |
| **True Negative (TN)** | Модель корректно промолчала на чистом участке кода. | Чистый рефакторинг не вызвал необоснованных комментариев. |

### 3.2. Математические формулы метрик

$$\text{Precision (Точность)} = \frac{TP}{TP + FP} \times 100\%$$
*(Метрика защиты от спама: показывает долю полезных замечаний среди всех опубликованных)*

$$\text{Recall (Полнота)} = \frac{TP}{TP + FN} \times 100\%$$
*(Метрика безопасности: показывает процент найденных критических дефектов от их общего числа в эталоне)*

$$\text{Hallucination Rate} = \frac{\text{Количество замечаний с вымышленным кодом/типами}}{TP + FP} \times 100\%$$

### 3.3. Методология оценки: LLM-as-a-Judge + Детерминированные линтеры
Для автоматического расчета $TP / FP$ в CI-контуре используется связка двух инструментов:
1. **Детерминированный валидатор (AST-парсер):** 
   - Автоматически проверяет синтаксическую валидность предложенного кода в Suggestions (код компилируется без ошибок).
2. **Модель-судья (LLM-as-a-Judge):**
   - Получает на вход эталонное описание бага (Ground Truth) и фактический комментарий AI-ревьюера.
   - Оценивает по рубрикатору:
     * **Groundedness (1/0):** Строго ли опирается замечание на код, или это выдумка?
     * **Classification (TP / FP):** Совпадает ли выявленная проблема с эталонной?
     * **Tone (1/0):** Инженерный, конструктивный тон без агрессии и поучений.

## 5. Критерии приемки (Quality Gates & DoD)

| Метрика | Минимальный порог | Статус | Назначение |
| :--- | :--- | :--- | :--- |
| **Coalescing Success** | **100%** | **BLOCKER** | Отмена устаревших задач при частых push-событиях. |
| **Sandbox Network Isolation**| **100%** | **BLOCKER** | Полная изоляция контейнера песочницы от внешней сети. |
| **Total Precision** | **$\ge 85\%$** | **BLOCKER** | Доля реальных багов (не более 15% шума). |
| **Critical Recall** | **$\ge 75\%$** | **BLOCKER** | Полнота нахождения уязвимостей безопасности. |
| **Hallucination Rate** | **$< 3\%$** | **BLOCKER** | Доля замечаний с вымышленным кодом/библиотеками. |
| **Batch Review Schema** | **100%** | **BLOCKER** | Публикация единым запросом `POST /reviews` без 422 ошибок. |
| **P95 Latency (DiffEngine)** | **$\le 40$ сек** | **MAJOR** | Скорость экспресс-анализа стандартного PR. |
