## 2. Тестирование микросервисов и архитектурных инвариантов

### 2.1. Схлопывание задач (Coalescing Engine, Р-2)

- **Бизнес-цель:** Защита бюджета токенов LLM при частых пушах разработчика в один и тот же PR.
- **Ключ схлопывания:** Кортеж `(installation_id, repo_id, pr_number)`.
- **Тест-кейсы QA:**
  1. **Серия быстрых пушей:**
     - **Действие:** Эмулируем 3 события `push` в один PR с интервалом в 2 секунды (хэши: `sha_1`, `sha_2`, `sha_3`).
     - **Ожидание:** Первые две задачи для `sha_1` и `sha_2` переводятся в статус `state = 'cancelled'`. В работу берется **только последняя задача** с актуальным `head_sha = sha_3`.
  2. **Поздняя отмена (Worker in-flight cancel):**
     - **Действие:** Новый push приходит в момент, когда воркер уже выполняет анализ старого `sha_1`.
     - **Ожидание:** Воркер получает сигнал прерывания (или Publisher проверяет актуальность перед отправкой) и отменяет публикацию устаревших замечаний.

### 2.2. WebHook Processor («Дежурный по GitHub»)

- **Что тестирует QA:**
  1. **Проверка HMAC-подписи:** Вебхуки с некорректным или отсутствующим `X-Hub-Signature-256` отклоняются со статусом `401/403`.
  2. **Идемпотентность (Idempotency Key):** Повторная отправка идентичного вебхука с тем же `X-GitHub-Delivery` не создает дублирующую задачу в RabbitMQ.
  3. **Быстрый ACK:** Обработка и подтверждение приема вебхука выполняется за $< 500$ мс.

### 2.3. Маршрутизация и контракт движков анализа (DiffEngine vs SandboxEngine, Р-3)

- **Архитектурный стандарт:** Единый контракт выходных данных `Finding[]` для обоих движков.
- **Что тестирует QA:**
  1. **Маршрутизация (Router Policy):**
     - Если в конфигурации проекта указан базовый аудит $\to$ задача идет в быстрый **DiffEngine** (SLA $\le 40$ с).
     - Если активированы правила глубокого анализа/выполнения кода $\to$ задача направляется в **SandboxEngine**.
  2. **Совместимость контракта:** Выходной payload находок от обоих движков строго валидируется единой Pydantic-схемой `Finding[]`.

### 2.4. Изоляция и безопасность SandboxEngine (Р-4)

- **Архитектурный стандарт:** Контейнер песочницы запускается контроллером снаружи, монтирует клон репозитория в режиме read-only.
- **Что тестирует QA:**
  1. **Zero-Network Isolation (`--network=none`):**
     - **Тест:** Тестовый код внутри песочницы пытается открыть исходящий сетевой сокет (HTTP-запрос / DNS-lookup).
     - **Ожидание:** Запрос немедленно блокируется на уровне ядра ОС. Сеть полностью недоступна.
  2. **Secret Sanitization (Изоляция токенов):**
     - **Тест:** Инспекция переменных окружения (`env`) внутри запущенного контейнера SandboxEngine.
     - **Ожидание:** Внутри контейнера **полностью отсутствуют** токены доступа к GitHub API, токены БД и ключи LLM-провайдеров. Ключи остаются исключительно на хост-контроллере.

### 2.5. Публикация результатов: Batch Review (Р-5)

- **Архитектурный стандарт:** Запрещена отправка множества одиночных комментариев. Публикация выполняется **единым батч-запросом**.
- **Эндпоинт:** `POST /repos/{owner}/{repo}/pulls/{pull_number}/reviews`
- **Что тестирует QA:**
  1. **Формирование Batch Payload:** Все найденные замечания упаковываются в массив `comments: [{path, line, body}]`, а общее заключение — в поле `body` ревью с вердиктом `COMMENT` / `REQUEST_CHANGES`.
  2. **Hunk Matching (Защита от сбоя координат):**
     - **Тест:** Модель вернула замечание на строку вне зоны измененного дифа.
     - **Ожидание:** Валидатор отсекает строку из массива `comments` и переносит замечание в текст общего резюме, предотвращая ошибку `422 Unprocessable Entity` от GitHub API.
  3. **Идемпотентность по `findings_hash`:** Повторная отправка идентичного батча не порождает дублирующих ревью в PR.
  4. **Поддержка 1-Click Suggestions:** В поле комментария формируется синтаксис `suggestion ... `, отображающий рабочую кнопку применения фикса в UI GitHub.

### 2.6. Инфраструктура и безопасность (RabbitMQ, Sub-network, JWT)

- **Durable Queues & Dead-Letter Queue (DLQ):** При аварийном падении воркера сообщение не теряется, а возвращается в очередь. Невалидные сообщения после 3 попыток отправляются в DLQ.
- **Sub-network Isolation:** Порты RabbitMQ, базы данных PostgreSQL и воркеров закрыты для внешнего трафика и доступны только внутри внутренней сети.
- **JWT Auth:** Все запросы к API Server требуют валидный Bearer-токен. Без токена или с просроченным токеном $\to$ `401 Unauthorized`.

## 3. Методология оценки качества LLM (LLM Evaluation & DoD)

### 3.1. Матрица ошибок и алгоритм One-to-One Matching

Для строгого расчета метрик используется детерминированный алгоритм сопоставления фактических находок модели ($A$) с эталонными дефектами ($E$) из спецификации теста:

```
                  ┌─────────────────────────────────────────┐
                  │ Ground Truth Дефекты (E) из spec.yaml   │
                  └────────────────────┬────────────────────┘
                                       │
                                       ▼  (One-to-One Bipartite Matching)
                  ┌─────────────────────────────────────────┐
                  │ Фактические находки модели (A)          │
                  └────────────────────┬────────────────────┘
                                       │
         ┌─────────────────────────────┼─────────────────────────────┐
         ▼                             ▼                             ▼
   [Успешная пара]             [Лишняя находка]              [Пропуск дефекта]
      (e_i ↔ a_j)                 (a_k без пары)                (e_m без пары)
          │                             │                             │
          ▼                             ▼                             ▼
   True Positive (TP)          False Positive (FP)           False Negative (FN)
```

1. **Правило сопоставления:** Находка $a_j$ сопоставляется с эталонным дефектом $e_i$, если:
   - Совпадает путь к файлу (`file_path`).
   - Номер строки находится в допустимом окне допуска ($\pm 2$ строки от эталона).
   - Тип и семантика проблемы согласуются по оценке AST-валидатора или модели-судьи.
2. **Классификация результатов:**
   - **True Positive (TP):** Ожидаемый дефект $e_i$ успешно сопоставлен ровно с одной фактической находкой $a_j$.
   - **False Positive (FP):** Фактическая находка $a_k$ не имеет пары в Ground Truth (ложное срабатывание / галлюцинация) **ИЛИ** является повторным дубликатом на уже закрытый дефект $e_i$.
   - **False Negative (FN):** Эталонный дефект $e_m$ **остался без пары** (модель промолчала на месте реального бага).
   - **True Negative (TN):** Чистый участок кода, на который модель обоснованно не оставила замечаний.

### 3.2. Математические формулы метрик

$$\text{Precision (Точность)} = \frac{TP}{TP + FP} \times 100\%$$
_(Доля реальных багов среди всех опубликованных замечаний — защита разработчиков от шума)_

$$\text{Recall (Полнота)} = \frac{TP}{TP + FN} = \frac{TP}{|E|} \times 100\%$$
_(Процент найденных дефектов от общего числа заложенных в Ground Truth — защита от пропуска уязвимостей)_

$$\text{Hallucination Rate} = \frac{\text{Количество замечаний с вымышленным кодом/типами/библиотеками}}{TP + FP} \times 100\%$$

### 3.3. Автоматизированная оценка: Детерминированные линтеры + LLM-as-a-Judge

1. **Детерминированный валидатор (AST-парсер):**
   - Проверяет синтаксическую валидность предложенного кода в Suggestions (код парсится и компилируется без синтаксических ошибок).
2. **Модель-судья (LLM-as-a-Judge):**
   - Применяется для верификации смыслового соответствия пары $(e_i, a_j)$ по рубрикатору:
     - **Groundedness (1/0):** Строго ли замечание опирается на переданный контекст дифа?
     - **Semantic Alignment (1/0):** Указывает ли находка на ту же корневую причину, что заложена в Ground Truth?
     - **Tone (1/0):** Корректный технический тон без агрессии и поучений.

## 4. Эталонный набор тестовых данных (Golden Dataset)

### 4.1. Структура фикстур в репозитории

Сценарии версионируются в каталоге `tests/golden_dataset/` с единым форматом поставки:

```
tests/golden_dataset/
├── TC-01_clean_code/
│   ├── diff.patch
│   └── spec.yaml
├── TC-02_secret_leak/
│   ├── diff.patch
│   └── spec.yaml
...
└── TC-09_sandbox_isolation/
    ├── diff.patch
    └── spec.yaml
```

**Формат `spec.yaml` (Ground Truth контракт):**

```yaml
id: 'TC-03'
title: 'SQL Injection via string formatting'
expected_verdict: 'REQUEST_CHANGES'
expected_findings:
  - file: 'app/db.py'
    line_range: [42, 45]
    severity: 'HIGH'
    category: 'SECURITY'
    defect_type: 'sql_injection'
```

## 5. Критерии приемки (Quality Gates & DoD)

| Метрика                       | Минимальный порог | Статус      | Назначение                                                       |
| :---------------------------- | :---------------- | :---------- | :--------------------------------------------------------------- |
| **Coalescing Success (Р-2)**  | **100%**          | **BLOCKER** | Отмена устаревших задач при частых push-событиях.                |
| **Sandbox Isolation (Р-4)**   | **100%**          | **BLOCKER** | Полная сетевая изоляция и отсутствие секретов в песочнице.       |
| **Total Precision**           | **$\ge 85\%$**    | **BLOCKER** | Доля реальных багов (не более 15% шума и ложных срабатываний).   |
| **Critical Recall**           | **$\ge 75\%$**    | **BLOCKER** | Полнота нахождения уязвимостей безопасности и критических багов. |
| **Hallucination Rate**        | **$< 3\%$**       | **BLOCKER** | Доля замечаний с вымышленным кодом/библиотеками.                 |
| **Batch Review Schema (Р-5)** | **100%**          | **BLOCKER** | Публикация единым запросом `POST /reviews` без 422 ошибок.       |
| **P95 Latency (DiffEngine)**  | **$\le 40$ сек**  | **MAJOR**   | Скорость экспресс-анализа стандартного PR.                       |
