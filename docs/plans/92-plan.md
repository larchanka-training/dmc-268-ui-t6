# Implementation Plan: #92 — ожидание репозиториев после обновления доступа

Refs: [larchanka-training/dmc-268-ui-t6#92](https://github.com/larchanka-training/dmc-268-ui-t6/issues/92).

## Overview

После успешного OAuth, начатого кнопкой «Обновить доступ», страница репозиториев
автоматически повторяет запрос списка каждые **5 секунд в течение 120 секунд**.
Пользователь видит состояние ожидания; новые репозитории появляются из кеша TanStack
Query без перезагрузки страницы. По окончании окна отображается понятное сообщение
с кнопкой ручного обновления. Уход со страницы прекращает опрос. Обычный вход не
запускает эту процедуру.

## Architecture Decisions

1. **Явно различать причину OAuth.** Добавить небольшой lifecycle intent рядом с
   существующим `features/auth/lib/returnTo.ts`, используя sessionStorage, чтобы
   намерение переживало переход на GitHub. Кнопка сохраняет pending intent и
   `/repositories` как return route. Только успешный `CallbackPage` переводит его
   в ready; ошибки OAuth, отсутствующий code и неуспешный обмен очищают intent.
   Обычный `LoginButton` очищает прежнее намерение перед началом нового входа,
   чтобы отменённый через browser Back refresh не активировался при другом OAuth.
   Страница репозиториев читает ready без записи во время render и удаляет его
   после запуска процедуры. Не выводить intent из наличия репозиториев или из
   общего return route. Границы хранения проверять как неизвестный ввод, хранить
   лишь UI metadata; списки репозиториев остаются в TanStack Query.
2. **Ограниченное окно, без ложного признака готовности.** В существующем API нет
   статуса onboarding или списка ожидаемых repository IDs. Поэтому опрос идёт
   всё окно независимо от пустого/непустого списка и появления первой новой
   строки. Первая новая строка не доказывает, что все установки обработаны.
   120 секунд согласуются с существующей подсказкой о задержке до нескольких
   минут; интервал 5 секунд ограничивает нагрузку примерно 24 запросами за окно
   (включая немедленный запрос, без запроса на самой границе 120 секунд).
3. **Кеш и запросы принадлежат entity.** Использовать существующий
   `useRepositories().refetch`, сохранив текущий Zod parsing и
   `REPOSITORIES_QUERY_KEY`. `fetchRepositories` принимает optional
   AbortSignal; queryFn передаёт signal TanStack Query в уже поддерживающий его
   apiClient. Не создавать второй список в Zustand или локальном React state.
4. **Время и жизненный цикл принадлежат странице.** Небольшой hook внутри slice
   `pages/repositories` управляет абсолютным deadline и состояниями idle,
   waiting, timedOut. Немедленный запрос после запуска не должен зависеть от
   глобального `staleTime: 30_000`. Таймеры вызывают query refetch,
   одинаковые запросы не перекрываются и не отменяют друг друга.
   `cancelRefetch: false` сохраняет активный GET; немедленный refetch планируется
   через отменяемую microtask. Query остаётся enabled: focus и invalidation от
   mutations продолжают работать.
   Проверять deadline внутри callback таймера перед каждым новым запросом,
   чтобы задержанный background timer не продлевал окно. На deadline отключить
   интервал независимо от settlement активного GET; таймеры убрать при unmount.
   Не запускать параллельный GET, если предыдущий ещё не завершён.
   AbortSignal отменяет активный запрос,
   когда последний наблюдатель уходит со страницы. StrictMode не теряет intent
   и не создаёт второй loop. Intent удаляется при старте, поэтому reload
   или повторное посещение страницы не возобновляет автоматический цикл.
   При StrictMode rehearsal первый штатный GET Query отменяется AbortSignal,
   повторный GET завершается, затем работает ровно один интервал без overlap.
5. **Понятная обратная связь.** Во время waiting показать info Alert со spinner
   и текстом «Обновляем список репозиториев после авторизации через GitHub.
   Это может занять до двух минут». Существующие строки и настройки доступны.
   На timedOut убрать spinner, показать «Автоматическое обновление завершено.
   Если нужный репозиторий ещё не появился, обновите список вручную» и кнопку
   «Обновить список».
   Кнопка находится под сообщением в Alert description, сохраняя ширину текста
   на мобильном экране. `RepositoryList.refreshing` показывает pending GET на
   обычной кнопке «Обновить».
   Это окончание окна проверки, а не утверждение о сбое
   onboarding. Кнопка и обычное «Обновить» выполняют один refetch, показывают
   pending состояние запроса, не запускают новый автоматический цикл. Сетевые
   ошибки используют существующий error Alert и не продлевают deadline.
6. **Минимальный scope.** Backend/API contract не меняется. Новые зависимости,
   изменения чужих PR и расширение общих router/provider правил не нужны.
   Если sessionStorage недоступен, авторизация продолжает работать, intent
   безопасно отсутствует; не заменять это глобальным опросом при каждом входе.

## Dependency Graph

`Кнопка обновления доступа → pending intent → успешный callback → ready intent`

`ready intent → RepositoriesPage lifecycle → useRepositories refetch → validated API → Query cache → RepositoryList`

Ошибки callback очищают intent. Deadline и уход со страницы выключают lifecycle.
Ручное обновление использует тот же Query cache без повторного OAuth.

## Tasks and Checkpoints

Подробные критерии и файлы — в [92-todo.md](92-todo.md).

1. Сохранить отдельное намерение обновления доступа при запуске OAuth.
2. Активировать намерение только после успешного callback.
3. Добавить ограниченный опрос, ожидание и ручное обновление.
4. Проверить lifecycle-регрессии, документацию и все gates; провести независимые
   Standards/Spec reviews, затем опубликовать PR.

После задач 1–2 проверить ordinary login и callback failures. После задачи 3
проверить delayed empty/nonempty lists, deadline и cleanup. Перед публикацией
все пункты todo и обязательные проверки должны быть завершены.

## Public Test Boundaries and TDD

- `RepositoriesPage`: действия пользователя, видимые строки/Alert, число и
  время GET `/repos`, прекращение новых запросов после navigation/unmount.
- `CallbackPage`: успешный/неуспешный обмен и последствия для последующего
  посещения страницы; ordinary login и StrictMode.
- `LoginButton`: ordinary login после отменённого refresh и logout очищает
  намерение перед callback, который не активирует ожидание репозиториев.
- Публичные auth intent helpers: lifecycle через sessionStorage, malformed
  input и недоступное хранилище. Не тестировать приватные детали hook.
- API seam: валидированные данные и передача AbortSignal сетевому вызову.

На каждой задаче сначала один падающий тест поведения, затем минимальная
реализация. Использовать fake timers с `act`, буквальные 5000/120000 в ожиданиях,
не импортировать runtime constants для расчёта expected values. Component tests
начинаются с jsdom directive и содержат cleanup. Не добавлять отдельные waitFor
timeouts. Проверить повторные mount и StrictMode, включая unmount с активным GET.

## Risks and Mitigations

| Risk                                                            | Mitigation                                                                      |
| --------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| Непустой устаревший список ошибочно останавливает polling       | Опрос не зависит от длины списка; отдельная регрессия old → old + new.          |
| Новая строка появляется, но UI обещает полную синхронизацию     | Не объявлять завершение onboarding; весь цикл ограничен временем.               |
| Intent переживает ошибку OAuth и запускает опрос при входе      | Очистка всех callback error exits и one-time consume; отдельные тесты.          |
| StrictMode съедает intent или удваивает timer                   | Peek during render, consume in effect, cleanup и StrictMode тест.               |
| Свежий Query cache скрывает первый GET после возврата           | Явный немедленный refetch; тест с preseeded cache.                              |
| Медленный GET и таймер продлевают окно либо перекрывают запросы | Query deduplication, абсолютный deadline, AbortSignal и тест deferred response. |
| Browser timer throttling запускает запрос после deadline        | Проверять текущее время перед интервальным запросом.                            |
| Concurrent PR ownership меняется                                | Повторить gh pr list/files перед правками и публикацией.                        |

## Verification and Publishing

Обязательные frontend gates: `pnpm lint`, `pnpm check-types`,
`pnpm format:check`, `pnpm test`, `pnpm build`, `pnpm verify:prod-bundle`.
До полного прогона запускать затронутые тесты через `pnpm exec vitest run ...`.
Проверить пользовательский flow с задержанным ответом/новым репозиторием,
таймаутом и уходом со страницы; реальный worker race может потребовать staging,
его наличие не блокирует детерминированные регрессии на публичной границе.

Publisher следует pull-request skill: Conventional Commit с `Refs #92`,
четыре секции PR `What` / `Why` / `How to verify` / `Refs`, без closing keywords
и Development-panel link; stage явные пути и tracked файлы, без `.pnpm-store/`.
Issue принимает и закрывает техлид; необходим approving review на текущем head
и resolved threads до merge. Автоматическое merge не входит в этот план.
