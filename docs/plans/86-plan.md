## Exact issue context

Название: **[ui] Фильтры: отложенная запись q на устаревшем URL при медленном коммите роутера**.
Состояние: OPEN; метка: bug; комментариев при чтении нет. Ниже тело issue без изменений.

> ## Background
>
> В ui#84 поиск по замечаниям на странице прогона держит текст в локальном состоянии. Параметр `q` пишется в URL через 250 мс после последнего нажатия (`replace`). Код: `src/features/finding-filters/model/useQueryText.ts` и `useFindingFiltersParams.ts`.
>
> `RouterProvider` из react-router 8.4 коммитит состояние роутера внутри `React.startTransition`. Поэтому роутер может уже перейти на новый адрес, а страница ещё отрисована со старым. Отложенная запись `q` строится на последнем отрисованном URL. Если она срабатывает в этом окне, получается одно из двух:
>
> - **Утечка `q` на другой прогон.** Пользователь набрал текст и ушёл на другой прогон в первые 250 мс, а новая страница рендерится медленно (большой дифф, первая загрузка lazy-чанка). Тогда к адресу этой страницы добавляется `?q=…`.
> - **Отмена «назад».** Если нажать «назад» и печатать, пока коммит ещё идёт, запись строится на старой базе. Она возвращает фильтры, которые «назад» только что сняли.
>
> Воспроизведено в ревью ui#84, раунд 2, пробами с искусственно медленным коммитом (пробы B, B2, F, F2). При обычных таймингах в браузере «назад», переход на другой прогон и перезагрузка работают.
>
> В ui#84 окно сознательно оставлено и записано в `docs/FRONTEND_ARCHITECTURE.md` §2 «Состояние в URL» как ограничение. Прототип закрыл все пробы. Он подписывается на роутер через `UNSAFE_DataRouterContext` → `router.subscribe` и ведёт базу записи по текущему адресу роутера. От него отказались, потому что это внутренний API react-router без гарантий semver.
>
> ## Scope
>
> - Закрыть окно медленного коммита. Подойдёт любой из путей:
>   - публичный API react-router, если в новых версиях появится подписка на адрес роутера до коммита React;
>   - изолированный адаптер над `UNSAFE_DataRouterContext` с фолбэком, тестом-канарейкой на обновление роутера и записью в FA;
>   - другой механизм, о котором договорится команда.
> - Тесты с детерминированно медленным коммитом: lazy-маршрут или Suspense с промисом, который резолвится вручную. Не сиблинги, которые жгут CPU.

> - [ ] Нажатие «назад» во время медленного коммита и последующий набор не возвращают фильтры, которые «назад» сняло.

## Findings and architecture decisions

1. `useQueryText` хранит текст и таймер локально. Его cleanup и синхронизация по
   `navigationKey` происходят после коммита, поэтому сами окно не закрывают.
   `useFindingFiltersParams` имеет `written` и очередь `ownSearches`, но также
   узнаёт о внешней навигации только из закоммиченных `useLocation`/effects.
2. Проверен установленный react-router 8.4.0: `lib/components.js` подписывает
   RouterProvider на router и вызывает `React.startTransition`; `useSearchParams`
   в `lib/dom/lib.js` захватывает отрисованные параметры. `router.state` и
   `router.subscribe` в `lib/router/router.d.ts` прямо помечены
   `@private PRIVATE - DO NOT USE`. `unstable_useRouterState` читает React
   contexts, поэтому не является гарантированной подпиской до коммита.
   Явная передача router instance сама по себе не делает этот API публичным.
3. Использовать разрешённый issue путь: маленький адаптер в
   `src/features/finding-filters/model/` — единственное место импорта
   `UNSAFE_DataRouterContext` и обращения к приватным state/subscribe.
   Остальная feature работает через типизированный минимальный интерфейс:
   фактическая location/history action и уведомление до коммита.
   Подписка синхронно обновляет refs/идентичность навигации; её cleanup обязателен.
   Не выключать transitions глобально и не использовать flushSync для поиска.
4. На внешней навигации актуализировать базу записи до коммита React. Различать
   собственные записи и внешние POP/PUSH/REPLACE; POP всегда внешний даже при
   совпадающем search. Запись от старого run/pathname не должна уходить на новый
   адрес. В том же прогоне база после POP — фактический новый URL, старые
   `file`/`severity` не восстанавливаются. Проверять pathname вместе с search/key:
   одинаковый search у двух прогонов не означает собственную запись.
   Не позволять запоздалому effect от старого render откатить refs к старой базе.
5. Сохранить отмену незаписанного текста при внешней навигации. Реализация
   может отменять таймер до коммита либо отклонять устаревшую запись у границы
   записи; выбор внутреннего механизма не меняет seam тестов. Учитывать ввод
   после POP, пока старое поле ещё доступно: он не должен воскресить снятые
   фильтры. Собственные незакоммиченные select+query и два select сохраняют оба
   изменения. Поле не теряет символы и каретку при собственных записях.
6. Fallback при отсутствии data router/ожидаемой возможности — работа через
   публичные rendered hooks без падения. Документировать предел этого режима,
   не выдавать его за защиту от окна до коммита. Canary проверяет установленный
   router и адаптер в реальном RouterProvider, чтобы upgrade не ушёл молча в
   fallback. Не перехватывать произвольные ошибки навигации как несовместимость.
7. Обновить только относящийся к гонке текст FA §2: убрать закрытое ограничение,
   описать адаптер, fallback, cleanup и upgrade canary; сохранить остальную FA.
   Новые зависимости, API/backend и визуальные изменения не нужны.

## TDD boundary and acceptance verification

Согласованный seam: пользовательский ввод/навигация → фактический URL роутера
при ещё не разрешённом Suspense. Не тестировать внутренние refs или названия
функций. Использовать RouterProvider как в app (`react-router/dom`), fake timers
для 249/250 мс и вручную разрешаемый promise для задержки коммита. Перед
ассертом обязательно доказать, что router уже на новом адресе, а старое поле
ещё отрисовано. Проверять URL до разрешения promise и после финального коммита.

| AC                               | Доказательство                                                                                                                                         |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Нет утечки q на другой прогон    | Набрать → перейти раньше 250 мс → удерживать Suspense → продвинуть debounce → новый pathname и отсутствие q → разрешить promise и перепроверить        |
| POP не возвращает снятые фильтры | История с разными file/severity → POP → удерживать коммит → ввод в старое поле → debounce → снятые file/severity не появились; проверить после коммита |
| Стабильные тесты, FA обновлена   | Promise gate вместо busy loop; повторный прогон новых тестов с обычными параллельными workers; FA §2 описывает фактическое решение                     |
| Существующее поведение           | Имеющиеся tests поиска, фильтров, reset, same-tick select/query, caret, history; fallback и upgrade canary                                             |

Новые тесты обязаны падать на исходной реализации. После GREEN временно
выключить защиту и подтвердить RED, затем восстановить решение.

`pnpm build`, `pnpm verify:prod-bundle` (после build). Не запускать одновременно
сборку и проверку её артефакта. Все результаты и RED/GREEN записать в todo.

Браузер: обычные ввод, select, reset, back/forward, переход на другой прогон,
reload в обеих темах; desktop и 390px, keyboard/focus, нет горизонтального
scroll. Медленный коммит доказывают детерминированные regression tests;
браузер не заменяет их случайными таймингами.
